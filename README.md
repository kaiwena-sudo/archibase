# archibase

**The only structured, license-clean, machine-native floorplan corpus. Built for spatial AI, generative design, and architecture agents.** 📐🏗️

Agents get real floor plans as room graphs and metric geometry and pay per call in USDC on Base with [x402](https://x402.org) (v2): **$0.02 per search** and **$0.10 per plan's geometry**.

Stack: Hono on Node (portable to Cloudflare Workers), `@x402/hono` + `@x402/evm` for payments, and a JSON file or Supabase for storage.

```
src/index.ts            routes, query validation, discovery document, server entry
src/middleware/x402.ts  x402 gateway: config, facilitator client, X-PAYMENT alias, JSON 402 body, dev mock facilitator
src/db/client.ts        PlanStore: JSON file (default) or Supabase PostgREST
src/db/vectors.ts       VectorStore: geometry files (default data/vectors) or an https bucket
src/db/validate.ts      record + rights validation used by the seed script
src/units.ts            metric storage, imperial presentation
db/schema.sql           Supabase table + RLS policy
scripts/demo.ts         end-to-end walkthrough (simulated payment)
scripts/pay.ts          real paying client (signed EIP-3009 USDC, Base Sepolia)
```

## Endpoints

| Method | Path | Paid | Description |
|---|---|---|---|
| GET | `/.well-known/x402.json` (also `/.well-known/x402`) | no | Discovery: resources, input/output JSON Schemas, price, network, asset, `payTo` |
| GET | `/api/v1/plans/search` | **$0.02 USDC** | Query: `bedrooms`, `m2_min`, `m2_max` (or `sqft_min`, `sqft_max`), `style`, `built`, `source`, `include_duplicates`, `units`, `limit` |
| GET | `/api/v1/plans/{plan_id}/vector` | **$0.10 USDC** | One plan's geometry: room polygons (ids match the graph), doors, windows. `units=imperial` for feet |
| GET | `/` | no | Landing page for browsers (`Accept: text/html`); service info JSON for everything else |
| GET | `/llms.txt` | no | Plain-text summary of the API for AI tools |
| GET | `/health` | no | Liveness |

**MCP server.** `mcp/` is a separate package, `archibase-mcp`, that gives AI assistants (Claude, Cursor and others) search and geometry tools. It pays from a dedicated wallet, with a per-call price cap and a per-session budget. See [mcp/README.md](mcp/README.md).

**Landing page.** `src/site/landing.ts` renders the page and `llms.txt`. Prices and the base URL come from the running config; the catalogue counts are constants in that file. The example drawing is generated by `scripts/build-site-example.ts`. Set `CONTACT_EMAIL` to show an address for dataset-licence enquiries.

Every response includes a `Link: </.well-known/x402.json>; rel="x402-discovery"` header. Both paid routes also declare the x402 **Bazaar** discovery extension, so facilitators can index them.

### Repeated layouts and flagged records

Datasets repeat the same apartment on every floor of a building: in Swiss Dwellings, 20,008 of 44,946 apartments are copies of a layout already in the set (one estate has 107 identical flats). Search therefore returns **one plan per layout** by default, and every result carries `layout_copies`, the number of plans sharing that exact layout (1 = unique). Pass `include_duplicates=true` to get every copy.

A layout is identified by a fingerprint of its room graph: room types, sizes to 0.1 m², windows, fixtures and connections, ignoring node ids (`src/db/layout.ts`). Mirrored copies share a fingerprint. The lowest `plan_id` in each group is the one shown.

Records that are probably wrong are flagged and never served. Today the only flag is `multi_unit_suspect`: three or more kitchens in one "apartment", meaning the source merged several units (3 Swiss records).

### Free sample, counts and the explorer

Developers can look before they pay:

- `GET /api/v1/sample` returns a fixed set of about 20 real plans in the paid format (same filters, same fields), and `GET /api/v1/sample/{plan_id}/vector` returns their geometry. The set is bundled into the Worker (`src/site/sample-data.ts`, built by `scripts/build-sample.ts` from the live database), so it costs nothing to serve and can't be used to read the catalogue: nothing outside the fixed set is reachable.
- `GET /api/v1/count?…` returns how many plans a search would match (it takes the search filters), memoised for a minute per query so it can't become database load.
- `/explore` is a browser page over both: it draws the sample, shows live counts, and runs paid searches and geometry purchases from a browser wallet (it signs the same EIP-3009 payment as `@x402/fetch`, with no library) or an API key. `src/site/client/explore.js` is the script; run `npm run build:client` after editing it. `npx tsx scripts/e2e-explore.ts` tests the page in a real browser with a fake wallet.

### Agent skill: converting plans

`skills/archibase-plan-converter/` is a downloadable [agent skill](https://archibase.dev/skills) (`SKILL.md` plus references and a dependency-free Node script) that teaches any agent to turn a scan, drawing or description into the Archibase format: the agent reads the drawing and writes room outlines, doors and windows in metres; `scripts/archibase.mjs build` derives areas, links, window counts and bedroom/bathroom totals, enforces the record rules (including the licence rules) and refuses bad output; `render` draws the result as SVG or text for checking. Fed the geometry of real plans from the corpus it reproduced all 34 Swiss door/opening links and the window counts, and flagged a genuine kitchen/storage overlap in a ResPlan source plan.

After editing anything under `skills/`, run `npm run build:skill` (embeds it in `src/site/skill-bundle.ts`, served at `/skills`, `/skills/<name>.zip` and `/skills/index.json`). `tests/skill.test.ts` runs the script as an agent would and cross-checks it against the server's own validator, and fails if the bundle is stale.

### API keys (prepaid credits)

For trials and partners who don't pay per call with a wallet. A key (`X-API-Key` or `Authorization: Bearer ak_…`) is spent at the same prices as x402 and refunded when a request fails. `npx tsx scripts/credits.ts create --usd 2 --label "Acme trial"` prints a key once (only its SHA-256 hash is stored); `list`, `topup <id> --usd N` and `disable <id>` manage them. `GET /api/v1/account` shows a balance.

- **Keys:** `ak_` + 256 random bits, table `api_keys` (`db/schema.sql`), balances in USDC base units. Spending is one conditional database update (`spend_credits`), so concurrent requests cannot overspend.
- **Test keys:** rows marked `test` are only honoured by testnet deployments.

### Geometry

Search results carry `vector_schema_url`, which is the paid geometry URL when the plan has geometry and `null` when it doesn't. The URL is assigned by the API, never stored. The vector route checks that geometry exists **before** asking for payment, so an unknown plan is a free 404. Prices are set with `PRICE_USD` and `VECTOR_PRICE_USD`.

```json
{ "plan_id": "sd-1078-4c05a80dbbdb", "schema_version": 1, "units": "m", "crs": "site-local; +x east, +y north",
  "attribution": "Swiss Dwellings v3.0.0 by ... CC BY 4.0 ... Modified: ...",
  "rooms":   [{ "id": "bedroom_1", "type": "bedroom", "level": 1, "polygon": [[[[x, y], ...]]] }, ...],
  "doors":   [{ "type": "door", "level": 1, "polygon": [...] }, ...],
  "windows": [{ "level": 1, "polygon": [...] }, ...] }
```

Each `polygon` is a list of polygons, each `[outer ring, ...holes]`. On Node the files are read from `data/vectors/`. On Workers, upload that folder (including `index.json`) to a public bucket and set `VECTOR_STORE_URL` to its URL.

### Payment flow

1. **Malformed query → 400**, before the paywall, so agents never pay for a bad request.
2. **No payment → 402.** Terms are sent in the standard v2 `PAYMENT-REQUIRED` header (base64) and repeated in the JSON body:
   ```json
   {
     "x402Version": 2,
     "error": "Payment required",
     "payTo": "0xYourWallet",
     "resource": { "url": "...", "description": "...", "mimeType": "application/json" },
     "accepts": [{
       "scheme": "exact", "network": "eip155:8453", "amount": "20000",
       "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
       "payTo": "0xYourWallet", "maxTimeoutSeconds": 120,
       "extra": { "name": "USD Coin", "version": "2" }
     }],
     "acceptsInfo": [{ "assetSymbol": "USDC", "networkName": "Base" }]
   }
   ```
   `asset` is the USDC **contract address** rather than the string `"USDC"`, because clients need the address to sign the payment. `accepts` is passed through verbatim so an agent can copy an entry straight into its payment payload. Readable labels live in the index-aligned `acceptsInfo`.
3. **Payment present** (`PAYMENT-SIGNATURE`, or the legacy `X-PAYMENT`) → the facilitator verifies it → handler runs → payment is settled → **200** with the results and a `PAYMENT-RESPONSE` receipt header. If the handler fails, settlement is cancelled, so the agent is not charged.
4. **Facilitator unreachable or erroring → 503** `payment_facilitator_unavailable` with `Retry-After`. Raw facilitator error text is logged server-side, never sent to clients.
5. **Settlement fails after verification → 402** with a reason code such as `{"error": "insufficient_funds"}`, and no data.

Response body:
```json
{ "count": 1, "units": "metric",
  "filters": { "bedrooms": 3, "m2_min": 140, "m2_max": 230, "style": "modern", "built": null, "source": null },
  "results": [{ "plan_id": "ab-modern-3br-0004", "style": "modern", "total_area_m2": 208.1, "bedrooms": 3,
                "bathrooms": 2.5,
                "adjacency_graph": { "units": "m2", "nodes": [{ "id": "great_room", "type": "living_room", "area": 44.59 }, ...],
                                     "edges": [...] },
                "vector_schema_url": null, "provenance": { ... } }] }
```

### Units

Everything is stored metric: `total_area_m2` is the net interior area in m² (balconies and other exterior spaces excluded), room `area` values are in m², and vector geometry is in metres. Imperial is a presentation option:

- `units=imperial` returns `total_sqft` (whole sqft) and room areas in sqft, with `adjacency_graph.units: "sqft"`.
- `sqft_min`/`sqft_max` work too and are converted to m² (1 ft = 0.3048 m exactly). Using both `m2_*` and `sqft_*` in one query is rejected with a 400, before the paywall.

| `FACILITATOR_API_KEY` | (none) | Optional bearer token for the facilitator |

**Choosing a facilitator.** The public `x402.org` facilitator only settles on **Base Sepolia**. ## Data sources and provenance

Every record carries a `provenance` object, and buyers can filter on it (`built=true`, `source=habs`):

```json
"provenance": { "source": "habs", "built": true, "license": "public-domain",
                "author": "Historic American Buildings Survey", "source_url": "https://www.loc.gov/..." }
```

| `source` | What it is | Rules enforced by the validator |
|---|---|---|
| `synthetic` | Generated test inputs and made-up examples; not production catalogue records | `built: false` |
| `habs` | Library of Congress HABS/HAER/HALS measured drawings | `built: true`, `public-domain`, loc.gov `source_url` |
| `commissioned` | Paid work from students or firms | licence `owned`, `author`, and an internal `rights_ref` (signed agreement) |
| `dataset` | Third-party open dataset | `source_url`; CC-BY needs an `attribution` line |
| `ai_generated` | Output of Archibase's own models | `built: false` |

Only licences that allow resale are accepted: `public-domain`, `CC0-1.0`, `CC-BY-4.0`, and `owned` (Archibase holds the rights through its own work or a written assignment). Non-commercial and share-alike licences are rejected.

`rights_ref` is internal. It is never served: the JSON store strips it and Supabase column grants hide it.

### Loading data

```bash
npm run seed -- incoming/batch.json --dry-run   # validate only
npm run seed -- incoming/batch.json             # merge into DATABASE_URL (file or Supabase)
```

The validator also checks the graph: every edge must reference a real room, there must be no self-loops or duplicate ids, and the bedroom count must match the graph's bedroom rooms. Records must be metric (`total_area_m2`, `adjacency_graph.units: "m2"`). Room areas that don't add up to `total_area_m2` produce a warning. One invalid record aborts the batch unless you pass `--skip-invalid`. Keep imported plans in the ignored `incoming/` directory and include provenance and license details with each record.

### Swiss Dwellings (Archilyse, CC BY 4.0)

The complete imported catalogue is a deployment input and is not included in this repository. The public sample endpoint uses a fixed set of attributed plans in `src/site/sample-data.ts`. The importer supports a deterministic sample of the [Swiss Dwellings v3.0.0](https://zenodo.org/records/7788422) dataset (CC BY 4.0); each imported record carries its attribution and modification note.

```bash
# download swiss-dwellings-v3.0.0.zip from Zenodo (932 MB), then:
unzip -p swiss-dwellings-v3.0.0.zip '*geometries.csv' \
  | npm run -s import:swiss -- --out incoming/swiss --rate 150   # --rate 1 = all 45k
npm run seed -- incoming/swiss/plans.json
```

How the graph is derived (`scripts/import/swiss-dwellings.ts`):
- **Doors:** each door sits in the wall between two rooms, so the two rooms nearest its centre are linked.
- **Openings:** rooms whose outlines touch, with no wall between them, are linked as `opening`.
- **Entrance:** the front door links to a `building_access` node.
- **Maisonettes:** rooms containing stairs on consecutive floors are linked as `stair`.
- **Fixtures:** every room lists the fixtures recorded in it, e.g. `"fixtures": ["bathtub", "sink", "toilet"]`.
- **Bathrooms vs toilets:** a source `BATHROOM` with a bathtub or shower stays `bathroom` (1 bath). One with a toilet but no bath or shower becomes `toilet`, a WC counted as ½ bath. One with no recorded fixtures keeps the source's `bathroom` label.
- **Windows:** every room has a `windows` count. A window is credited to every indoor room it lights: a ribbon window spanning two rooms counts for both, and a window onto a balcony goes to the room, not the balcony.
- **Unlabelled rooms:** Archilyse's generic `ROOM` stays `type: "room"`; it is never presented as a bedroom. It gets an `inferred_use`:
  - `bedroom`: has daylight (a window, or a glazed door onto a balcony, loggia, terrace or winter garden), at least 6 m², and 3 or fewer connections;
  - `entry`: the front door opens into it;
  - `unknown`: anything else.

  `bedrooms` counts labelled bedrooms plus rooms inferred as bedrooms, and `bedrooms_inferred` says how many of those were inferred.

Only `geometries.csv` is read. The dataset's `locations.csv` and `location_ratings.csv` tie buildings to addresses and are deliberately not used. `style` is `"unspecified"` because the dataset has no style data.

### Hong Kong 3D Indoor Map (Lands Department, HKSAR)

The Lands Department's [3D Indoor Map](https://portal.csdi.gov.hk/csdi-webpage/dataset/landsd_rcd_1671437329821_60808) covers 787 buildings: offices, industrial buildings (flatted factories and godowns), MTR stations, shopping centres, government buildings, sports centres, hotels, and mixed residential towers. It is published as IMDF GeoJSON. The [CSDI Portal terms](https://portal.csdi.gov.hk/csdi-webpage/doc/TNC) allow commercial use free of charge, provided the Government and the CSDI Portal are named as the source and their ownership is acknowledged. The data is provided as is, and users indemnify the Government. Records use licence `HK-CSDI-TOU` and carry that attribution. Plan ids are `hk-<venue>-l<floor>` (`lm2` = 2 floors below ground).

```bash
python3 -m venv .venv-geo && .venv-geo/bin/pip install shapely
.venv-geo/bin/python -I scripts/import/hk-indoor.py incoming/hk --workers 8      # about an hour for all 787
npm run supabase:load -- incoming/hk/plans-*.json --vectors incoming/hk/vectors
```

How it is converted (`scripts/import/hk-indoor.py`):
- **One plan per floor**, with `building_type` taken from the venue category. LandsD's "businesscampus" is split into `industrial` or `office` by name; its "resort" venues are residential and mixed-use towers (`mixed`).
- **Spaces:** IMDF `room` is a tenancy (an office suite, shop, stall or whole flat), so it becomes `unit`; `unspecified` becomes `space`. Toilets, lifts, stairs, escalators, lobbies and corridors keep their roles. Voids carry no area.
- **Links:** an IMDF opening links the spaces it touches (`door`), and a main opening touching one space is the entrance. Corridors and lobbies that touch are linked as `opening`. Windows are matched to spaces by the dataset's own unit ids. Links between floors are not modelled.
- **Geometry:** WGS84 is projected to local metres around each building, with +y north (true orientation). Outlines are simplified by 5 mm and rounded to the millimetre, which shrinks files to about 42%. Typical room-area change is under 0.01% (worst case seen: 0.7%).
- **Repeated floors:** a floor identical to a lower floor of the same building is stored once, and `identical_levels` lists the others (3,802 floors merged).
- **Skipped:** floors with fewer than 3 spaces or under 20 m², and the ~1% of floors whose spaces overlap by more than 10%.

### ResPlan (Abouagour & Garyfallidis, CC BY 4.0)

[ResPlan](https://zenodo.org/records/20061236) holds 17,000 South Asian residential plans (apartments and houses) recovered from real-estate listings, with room polygons, doors, windows and a typed room graph. Plan ids are `rp-<resplan id>`. Take it from Zenodo or GitHub, which license the data CC BY 4.0; the Kaggle copy is labelled non-commercial.

```bash
python3 -m venv .venv-resplan && .venv-resplan/bin/pip install shapely networkx numpy
# download ResPlan_data.zip from Zenodo (107 MB) and unzip it into its own folder, then:
.venv-resplan/bin/python -I scripts/import/resplan.py <dir>/ResPlan.pkl incoming/resplan
npm run supabase:load -- incoming/resplan/plans-*.json --vectors incoming/resplan/vectors
```

How it is converted (`scripts/import/resplan.py`):
- **Safe loading:** the data is a Python pickle, which can run code when loaded. The importer only allows the Shapely, NetworkX and NumPy classes the file contains and refuses anything else.
- **Scale:** coordinates are normalised to a 256-unit image grid, not metres, and the stated net area is missing or wrong on about a third of plans. Each plan's scale comes from the listing's gross area instead (inner area + walls + balconies). This gives a median wall of 0.21 m and door of 0.91 m, so lengths are good to about ±2%. Geometry is flipped to +y up; compass orientation is unknown.
- **Edges:** `via_door` → `door`, `direct` → `opening`, `via_window` → `window` (e.g. a room looking onto a balcony), front door → `entrance_door` to an `outside` node. Source adjacencies become `opening` where the outlines touch with no wall between them for at least 0.6 m (3,546 kitchens open onto the living area this way). Otherwise they are dropped, except for a room with no other link, where they stay as `adjacent` (touching; no door or opening recorded).
- **Windows:** each window goes to the nearest indoor room within reach of its wall, else to a balcony.
- **Bathrooms:** the source doesn't separate full baths from WCs, so each counts as 1 bath.
- **Rejected (216 of 17,000):** wall thickness outside 0.08–0.5 m, net area outside 15–1,000 m², a bedroom outside 4–60 m², or rooms covering less than 70% or more than 115% of the floor (overlaps or unlabelled gaps). Slivers under 0.1 m² are dropped.
- **Takedowns:** the ResPlan authors run a takedown process for listing owners. IDs in `scripts/import/resplan-takedowns.json` are skipped; also delete them from the database.

## Wallets

`scripts/wallet.ts` sets up the two wallets for a first real payment on **Base Sepolia (testnet)**: a payee that receives USDC, and a test buyer that pays.

```bash
npm run wallet -- new archibase-payee --purpose payee   # prints the .env lines for the server
npm run wallet -- new test-buyer --purpose buyer
npm run wallet -- list                                   # names + addresses
npm run wallet -- balance test-buyer                     # USDC + ETH (needs sepolia.base.org)
npm run wallet -- env archibase-payee --buyer test-buyer # .env lines, no keys
```

1. Get test USDC for the buyer at [faucet.circle.com](https://faucet.circle.com). Choose **Base Sepolia** and paste the buyer's address.
2. The buyer needs **no ETH**. x402 `exact` payments are EIP-3009 `transferWithAuthorization` signatures: the buyer only signs, and the facilitator submits the transaction and pays the gas.
3. Run the server with the `env` lines in `.env`, then pay: `npm run wallet -- pay test-buyer "?bedrooms=2"`. This runs `scripts/pay.ts` with the buyer's key injected into that process only.

Keys are stored in `.wallets/<name>.json` (directory 0700, files 0600, git-ignored) and are never printed. They exist only on the machine that created them, so back up anything you care about, or recreate the wallets locally.

**Mainnet:** the tool refuses to create mainnet keys. To receive real money, use a wallet you control (a hardware wallet, Coinbase Wallet, or a Safe) and set only its **address** as `WALLET_ADDRESS`. Check it first with `npm run wallet -- check-address <0x...>`, which validates the checksum, rejects the zero address, and reports whether it is a contract (e.g. a Safe) or a plain account. Mainnet also needs a mainnet facilitator; see [Setup](#setup).

## Supabase

Plans live in `floor_plans` and geometry in `floor_plan_vectors` (`db/schema.sql`, safe to re-run).

**Access model.** The data is the product, so neither table is readable with Supabase's public `anon` or `publishable` key. Row-level security is on, with no policies for `anon` or `authenticated`. The API reads with the project's **secret** key (`sb_secret_...`, or the legacy `service_role` key), which stays on the server. To check: as `anon` or `authenticated` both tables return "permission denied"; as `service_role` they're readable.

**Loading** uses the Management API with a personal access token (`sbp_...`, from Account preferences → Access Tokens), so no service key is needed:

```bash
export SUPABASE_PROJECT_REF=<ref> SUPABASE_ACCESS_TOKEN=sbp_...
npm run supabase:load -- incoming/plans.json --vectors incoming/vectors --exclude-source synthetic --dry-run   # validate only
npm run supabase:load -- incoming/plans.json --vectors incoming/vectors --exclude-source synthetic
# full Swiss Dwellings set: import with --rate 1, then load every chunk
npm run supabase:load -- incoming/swiss/plans-*.json --vectors incoming/swiss/vectors
```

Every record is validated like `npm run seed` (one invalid record aborts the run) and upserted by `plan_id`, so re-running is safe. The loader also writes each plan's layout fingerprint and quality flags, then re-ranks repeated layouts across the whole table (`refresh_layout_ranks()` in `db/schema.sql`).

To recompute fingerprints for rows already loaded (or after changing the rules in `src/db/layout.ts`): `npx tsx scripts/supabase-layouts.ts` reports, `--apply` writes. If the Management API answers 502 on the final ranking step, run `select public.refresh_layout_ranks();` again; it is idempotent.

**Serving:** set `DATABASE_URL=https://<ref>.supabase.co` and `SUPABASE_KEY=<secret key>`. Geometry is then read from Supabase automatically (`VECTOR_STORE_URL` overrides this). Secret keys are sent in the `apikey` header; legacy JWT keys are also sent as `Authorization: Bearer`. The store calls PostgREST over `fetch` with no SDK, so it also runs on Cloudflare Workers.

The site's catalogue figures come from the `catalogue_stats` materialized view, refreshed after each load.

## Deploy to Cloudflare Workers

The same app runs on Workers via `src/worker.ts`. The Worker requires your own Supabase catalogue; the production catalogue is not included here. `WALLET_ADDRESS`, `DATABASE_URL`, and `SUPABASE_KEY` must be configured as Worker secrets. Wrangler checks for them before deployment, and the Worker returns a configuration error if they are missing.

```bash
# local (workerd): put development values in .dev.vars, e.g.
#   WALLET_ADDRESS=0x...
#   DATABASE_URL=https://<project>.supabase.co
#   SUPABASE_KEY=<secret key>
#   FACILITATOR_URL=mock
npm run dev:worker                       # http://localhost:8787
API_URL=http://localhost:8787 npm run demo

# production: add all required secrets in the Cloudflare dashboard, then deploy each Worker
# testnet Worker: WALLET_ADDRESS, DATABASE_URL, SUPABASE_KEY
# mainnet Worker: WALLET_ADDRESS, DATABASE_URL, SUPABASE_KEY, CDP_API_KEY_ID, CDP_API_KEY_SECRET
# FACILITATOR_API_KEY is optional when your facilitator requires a bearer token.
npm run deploy                               # testnet Worker
npm run deploy -- --env mainnet              # mainnet Worker, if enabled
```

Cloudflare environments have separate secrets. Add each Worker's full required set in the dashboard before its first deploy. Set `X402_NETWORK`, `PRICE_USD`, `FACILITATOR_URL`, and `PUBLIC_BASE_URL` in `wrangler.toml` or in the dashboard. `nodejs_compat` is required.

## Development

```bash
npm test              # vitest: unit + in-process HTTP/payment flow tests
npm run typecheck     # Node + Worker type-check
npm run typecheck:tests
```
CI (`.github/workflows/ci.yml`) runs type-check, tests and build on every push and PR.
